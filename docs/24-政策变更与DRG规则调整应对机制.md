## 二、应对机制:四步闭环

```
政策雷达(发现) → 影响评估(定性) → 版本化更新+回归(实施) → 切换留痕+简报(交付)
     ↑                                                                    │
     └────────────────── 反向侦测:月度对表一致率异常下降 ←──────────────────┘
```

### 第 1 步:政策雷达(发现变更)

- **固定信息源**:某地区医保局官网政策文件栏(ylbzj.cq.gov.cn)、国家医保局、国家中医药管理局、属地经办机构通知、院内医务科收文;
- **年度日历**(已知节奏写死):
  - **每年 Q4~次年 1 月**:关注下年度 DRG 付费预算、基础费率、机构系数、区域预算文件(现行为"年初按上年费率暂结,新费率确定后清算");
  - **每年 Q2~Q3(约 6~7 月)**:关注中医优势病种付费年度版(2025 版为 7 月 1 日施行)与细分组目录调整;
  - **不定期**:国家 DRG 分组方案大版本(2024-07 出 2.0 版,要求 12 月底前切换——此类切换有明确过渡期,雷达必须提前捕捉);
- **责任分工**:医务科负责收文登记(来源/文号/收到日期),项目组负责解读,信息科协助外网检索(内网机器不假设可直连互联网);
- **SLA**:文件到手后 **3 个工作日内**出《影响评估单》(变更类别/触碰的表与作业/工作量/风险)。

> **前提更正(2026-09-20)**:本步原按"**推送通道**"设计——医保发文 → 医院收文登记 → 项目组解读。**该通道不存在**:医保不逐份推送,只发布政策文件,由医院自行查阅,因此"收文台账"没有任何数据来源。替代方案见**第七节**——用 `s21_policy_watch.py` 的**文件指纹 + 事实抽取 + 与现行值比对**,把台账变成扫描的副产物,不再依赖有人登记。上面的年度日历保留(用于提醒主动去查),但已不是主要发现手段。

### 第 2 步:影响评估(定性)

用固定模板回答四个问题:①动了哪类(六分类)?②drg 库里哪些表受影响(dict_*/param_*/规则/白名单)?③哪些应用与作业受影响(引擎/模拟器/质控/对表/看板)?④历史数据口径是否受影响(决定是否重算与举证口径)。

### 第 3 步:版本化更新 + 回归测试(实施)——机制已在架构里

1. **只加不改**:字典/参数更新一律以**新 policy_version 插入**,不 UPDATE 旧版本(新旧并存,切换点可指定生效日期);ddlio 只执行 `src/sql/` 下新增版本化脚本,全程 sha256 留痕到 `ops_ddl_log`;
2. **回归门槛**:更新后跑全量回测(**3-7 月 N 例基线** + 每月新增官方返回,滚动扩充),**ADRG 一致率 ≥96.5%、四位码 ≥87.0% 为基线门槛**(2026-09-24 重沉降并留安全边际;分组方案类变更除外——那类变更的"一致率变化"本身就是变更内容,须人工归因确认);
3. **白名单联动**:凡触及中医规则/质控规则的变更,自动进入双主管(医务科+信息科主管)复审队列,规则与政策条款的挂接关系逐条更新;
4. **影子确认**:大版本变更(③④)先影子运行一个月(引擎新版本只对表不发布),与官方返回验证后再切应用层。

### 第 4 步:切换留痕 + 政策变更简报(交付)

- 切换后在 `ops_*` 记录:变更文件文号、生效日期、脚本 sha256、回归结论、双主管签认;
- 向院长/医务科发一页纸《政策变更简报》:变了什么、影响多少钱、我们要做什么——**这是管理层最关心的输出**;
- 历史举证能力:任何历史月份的预分组/盈亏都能按"当月适用 policy_version"复现,年终清算争议时逐笔可查。

## 三、反向侦测:月度对表本身就是政策变更探测器

这是本项目独有的优势:**每月官方返回与院内引擎的逐例对表,不仅是纠错工具,更是政策变更的预警信号。**

- **信号定义**:当月 ADRG 一致率较上月**下降超过 5 个百分点**,且院内无任何字典/参数/编码变更 → 触发"疑似医保侧规则调整"排查(优先核对:分组方案、中医入组规则、除外支付口径);
- 2026 年的历史已证明该信号有效:官方把"毫针为主手术"的病例归入 IU2F 而既有引擎归 IU25,正是靠对表发现的——将来医保侧任何"隐性规则变化"(不发文、只体现在结算结果里),月度对表都会把它暴露出来;
- 常态化要求:每月对表报告固定包含"一致率环比"一列,异常自动标红并进入巡检单。
- **落地状态**:**已生效**。s20 每次运行产出按月序列(见第六节),任一月份环比下降超 5pp 即自动写 `ops_alert`(`owner='s20'`)。**当前局限**:序列现为 2026-03~07 **五个点**,仍是对同一批 N 例官方返回的**回溯划分**,尚未逐月累积——真正的"滚动"要等每月新增官方返回导入后逐月长出来。这一点在向医务科解释预警含义时必须说清。

## 六、回归作业 s20 落地说明(2026-09-20)

第五节补强第 3 项已落地为 `src/etl/s20_regress.py`——这套机制里原本**唯一还靠人肉**的环节。改造前"变更后要不要放行"靠人工比对报告;现在是一条命令加一个判定。

| 能力 | 实现 |
|---|---|
| 全量回测 | 调用 `s11_adrg.run_backtest()`——**与 S11 报告同一函数**(S11 自带 `Grouper` 已删除),故回归判定与回测报告**不可能互相矛盾** |
| 门槛判定 | ADRG ≥96.5%、四位码 ≥87.0%、样本量 ≥500（**2026-09-24 按 3-7 月 N 例基线重沉降并留安全边际**：达成值 96.9%/88.1% 下方 0.4/1.1pp，容忍月度波动；此前 96.0%/81.3% 为 3-5 月 N 例基线），三项全过才 PASS |
| 一致率环比 | 与 `ops_regress_run` 上次运行对比,下降 ≥5pp 触发预警(即第三节反向侦测) |
| 按月滚动序列 | 每月 ADRG / 四位码一致率 + 环比,下降 ≥5pp 标注 |
| 异常标红 | 写 `ops_alert`(`owner='s20'`),查询即见 |
| 留痕 | `ops_regress_run`(每次一行,**含当次适用的门槛**)+ `ops_regress_metric`(ALL + 按月)+ `ops_run_log` |

**门槛为什么存进表里而不是写死在报告**:分组方案类变更(③)本身会移动门槛,历史判定必须能按"当时的尺子"复现,不能事后被重新判定。

**用法**:

```powershell
$env:DRG_ALLOW_DDL=1; python src/etl/s20_regress.py --note "2026 中医版规则更新"
python src/etl/s20_regress.py --dry      # 只看判定,不落库
```

**半自动执行（现行,2026-09-24 起）**:web 控制台「作业触发」→「回归门槛判定（s20）」一键触发——`jobs_api` 白名单作业（仅 `it` 角色）,后端自动注入写入门禁,运行留痕 `drg.ops_job_run`(30 天留存),前端轮询日志。**月度节奏由 s19 监护**:最近一次判据超过 35 天未执行,`ops_alert`(owner=s19)自动提示「回归判定超月未执行」,控制台「告警中心」可见——半自动模式不靠记忆。

**首轮实测(2026-09-20)**:

| 结算月份 | 例数 | ADRG 一致 | 四位码一致 | 环比 |
|---|---:|---:|---:|---:|
| 2026-03 | 185 | 93.5% | 81.1% | — |
| 2026-04 | 200 | 96.5% | 79.0% | +3.0 pp |
| 2026-05 | 167 | 98.2% | 84.4% | +1.7 pp |
| **合计** | **N** | **96.0%** | **81.3%** | — |

判定 **PASS**;月度一致率逐月上升,无异常。异常/未达标路径已用合成场景验证:门槛未达、环比下降、月度下降、样本量不足**四条规则均能命中并判 FAIL**。

**一个必须记住的坑**:月份键取 `settle_date`。该列 N/N 非空,但**混了带时区(`+00:00`)与不带时区两种格式**;pandas 3 对混合格式整列走快速路径会失败,`errors="coerce"` 会**静默丢掉 185 行**(整个 2026-03 从序列里消失)。必须用 `format="mixed"` 逐元素解析。源文件自带的 `settle_ym` 列只覆盖 200 例,不可作键。

**顺带修掉的一个缺陷**:`ops_alert` 原本每次刷新执行 `DELETE WHERE status='open'`——对单个生产者正确,对两个作业会**互相清空告警**。已加 `owner` 列,s19 / s20 各管各的(改造前遗留的 `NULL` 行仍归 s19)。

**门槛重沉降(2026-09-24,扩展至 3-7 月)**:

结算返回已扩展为 2026-03~07 共 **N** 例;同期引擎在住院天数口径上做了修复(docs/32)。以当前引擎重跑得 **ADRG 96.9%(823/849)、四位码 88.1%(748/849)**——四位码较上一运行(#10,81.4%)提升 **+6.7pp**。据此将门槛由 96.0%/81.3% 重沉降为 **96.5%/87.0%**——**留安全边际**(达成值 96.9%/88.1% 下方 0.4/1.1pp)。

|---|---|---:|---:|---|---|
| #9 | N(3-5月) | 96.0% | 81.3% | 96.0% / 81.3% | PASS |
| #10 | 849(3-7月,引擎修复前) | 96.9% | 81.4% | 96.0% / 81.3% | PASS |
| #11 | 849(3-7月,当前引擎) | 96.9% | 88.1% | 96.9% / 88.1% | PASS |

## 七、政策文件台账 s21(2026-09-20)——替换"政策雷达 + 收文台账"

**为什么改**:第 1 步原假设存在推送通道。使用方反馈**该通道不存在**——医保只发布政策文件,由医院自行查阅。没有收文来源,"收文台账"是无源之水;靠人通读 5 份 PDF(含 **1834 页**的国家方案)既不可持续也不可复现。

**替代机制(拉模式,可复现)**:把政策文件当作**可版本化的数据源**——

```
把新文件放进 原始资料/  →  python src/etl/s21_policy_watch.py  →  告诉你变了什么
```

| 能力 | 实现 |
|---|---|
| 文件台账 | 每份文件的 sha256 / 页数 / 表格数 / 行数 / **文号** / **施行日期**,自动登记到 `drg.dict_policy_doc` |
| 变更发现 | 与上次扫描按 sha256 比对 → 新增 / 移除 / **内容变更** |
| 事实抽取 | 从正文抽取政策要素(优势病种数、中治率、风险金、极高/极低占比、上传时限…),存 `drg.dict_policy_fact` |
| 与现行值比对 | 与 drg 库现行字典/参数比对 → 一致 / 不一致 / 仅登记 / 文档间冲突 / 待人工确认 |
| 影响评估单 | 对"不一致"项自动生成:变更类别 / 需更新的表 / 需重跑 / 谁签认 |

**首轮实测**:11 份政策文件全部登记,文号自动识别(`某地区医保局〔2025〕26/27号`、`渝医保办〔2025〕50/51号`),施行日期 2025-07-01;**组数 839 / QY 20 / 中医病组 10 / 中治率 60% 与系统现行值全部一致,无不一致项**。

### 三条必须说清的边界(决定这东西能不能被信任)

1. **sha256 是可靠信号,事实抽取不是**。文件有没有变,指纹说了算;变了什么,抽取只能**缩小阅读范围**,不能替代阅读——报告第五节会明确列出"仍需人工通读的部分"。
2. **PDF 抽数值天然不可靠**:页码被插进句子(`...支付标准-13-40%（含）...`),且数字可能在关键词**之前**("预留5%作为DRG付费风险金")。首版曾把风险金抽成 **50%**。因此加了三道防线:页码 artifacts 清理、**双向就近匹配**、合理性范围校验;再加**置信度分级**:
   - 结构解析值(组数 / QY)或 **≥2 个来源一致** → 才允许判"不一致";
   - **单源**文本值 → 只标"待人工确认",**绝不自动报警**;
   - 不同文档给出不同值 → 标"**文档间冲突**",两个都不信。
3. **扫描件 PDF**(无文本层)**抽不出任何东西**,只能人工读。

### 与 s20 构成两条独立通道

| 通道 | 依赖 | 覆盖 |
|---|---|---|
| s21(文档侧,主动) | **医务科 / 信息科**把文件放进 `原始资料/` | 政策**明文**变化——"发了文我们没看到" |
| s20(数据侧,被动) | 每月官方结算返回 | 医保侧**隐性**规则变化——"改了但没发文" |

> 二者互补,且**都不依赖推送通道**——这才是"没有收文渠道"这一约束下的可行解。

**文件放入责任人（已定）**：新政策文件由 **医务科 + 信息科** 获取并放入 `原始资料/`（2026-09-20 确认）。项目组不负责主动取件;文件放入后运行 `python src/etl/s21_policy_watch.py` 即完成登记与比对。`原始资料/` 新增/变更文件也会被 s21 按 sha256 自动识别。
