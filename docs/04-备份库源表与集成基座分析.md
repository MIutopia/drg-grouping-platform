# 备份库源表与集成基座分析

> 分析对象:`原始资料/数据库样表\入院诊断样表.xlsx` + `原始资料/数据库样表\建表脚本\`(31 个 SQL)
> 结论:医院已有一层备份库数据仓库,HIS 源表结构完全可追溯;此前两大悬案("其他诊断在哪"、"费用类别覆盖")**均已破解**
> 分析日期:2026-09-18

---

## 一、两个悬案破解

### 1. "其他诊断/其他手术"在 HIS 源表里有,且是一对多明细 ✅

备份库病案首页表(`源表(case_man)`)的建表脚本(住院病案首页.sql)完整暴露了 SBO 源库(HIS 生产库)的结构:

| 源表 | 内容 | 关键字段 | 对 DRG 的意义 |
|---|---|---|---|
| **SBO.dbo.源表(diagnosis)** | **诊断明细表,一诊断一行** | 列(hospital_no)、列(note)(名称)、**列(icd)(编码)**、列(kind_input)(1=中医 2=西医)、**列(order)(诊断序号)** | 其他诊断(分组 CC/MCC)直接取 列(order)≥2 的行;备份库首页表只取了 列(order)=1,**拍平是备份库设计选择,不是 HIS 限制** |
| **SBO.dbo.源表(operation)** | **手术明细表,一对多** | 列(id_parent)=源表(admission).列(serial)、列(code)(编码)、列(name) | 其他手术直接可取 |
| SBO.dbo.源表(admission) | 住院主表 | 列(serial)(首页序列)、列(hospital_no)(住院号)、入出院/床位/付费方式/治疗类别/质控 | 病例主索引 |
| SBO.dbo.源表(operate__apply) | 手术申请 | 列(hospital_no)、列(cut)(切口愈合等级) | 手术信息补齐 |
| SBO.dbo.源表(account)(+Link/Contact) | 患者档案 | 身份证/地址/电话 | 人口学 |

**结论:DRG 预分组引擎的诊断/手术输入,直接从 SBO 源表取全量明细,或扩展备份库新增"住院诊断明细表/住院手术明细表"两张同步表(与现有 ETL 风格一致)。之前按首页样表判断的"最大结构缺口"降级为"备份库扩展需求"。**

### 2. 床位/护理/材料/手术费全覆盖,靠统计码 22 档分类 ✅

住院费用.sql 注明费用源表为**三张**:源表(fee_check_in)(检查)/Cure_In(治疗)/Medicine_In(药品),统计码 `列(sort_code)` 22 档映射:

> 01 西药(01+卫生材=材料)/ 02 西药 / 03 草药 / 04 挂号 / **05 床位** / 06 诊察 / **07 护理** / 08 检查 / 09 化验 / 10 治疗 / **11 手术** / 12 救护车 / **13 材料** / 14 MRI / 15 CT / 16 彩超 / 17 输氧 / 18 输血 / **19 麻醉** / 20 麻醉相关 / 21 其他

- 此前样表"未见床位/护理/材料费"是因为:费用类别(检查/治疗/药品)只是**物理来源表**,统计码才是费用性质;样表中治疗类行统计码全 NULL,落到 ELSE 兜底类。
- ⚠️ 新质控点:**源表(fee_cure_in) 的 列(sort_code) 填充率需实测**(若大量为空,费用类型归类会失真,进而影响结算清单 115 项费用分类)。
- 医保结算关联源表:**SBO.dbo.源表(settle)**(列(bill_no)=医保结算ID、列(call_no)=医保就诊ID、列(city)=参保地、s_ma列(kind)=医保类型)——费用明细↔结算返回的金链路在源库就有。

## 二、现有备份库架构(可直接复用的集成基座)

医院 2026-09 刚建成一套数据仓库,本次改造**不必从零搭建**,可整体复用其架构模式:

```
SBO.dbo.* (HIS 生产库, SQL Server)
   │  历史同步 usp_Sync*_History + 增量同步 usp_Sync*_Incremental
   │  SyncControl 同步控制表 + SQL Server Agent 定时作业 + 夜间历史数据追赶
   ▼
备份库三库 ── records.dbo.out_medical_records        门诊病历
          ├─ med_record.dbo.源表(case_man)   住院病案首页(拍平版)
          ├─ med_record.dbo.源表(med_record) 住院入院记录
          ├─ caiwu.dbo.CostDetail_Snapshot             门诊费用快照
          └─ caiwu.dbo.CostDetail_Snapshot_hospitalization 住院费用快照(22档费用类型)
   │  12 个中文视图(入院/出院/病程/病案首页/长短期医嘱/处方/病历/药品利润/医生绩效)
   ▼
Metabase / SQLBot 报表消费(已有 BI 习惯)
```

**对 DRG 改造的意义:**

1. **集成层已存在**:只读直连、增量水位(列(time_input))、调度、去重保护、监控核查(全量核查_所有对象状态.sql)都是现成模式,DRG 侧新增同步对象直接照此风格扩展;
2. **建议新增的同步对象**:住院诊断明细(源表(diagnosis) 全量)、住院手术明细(源表(operation) 全量)、医保结算返回表(手工导入或后续接口)、收费项目字典与医保目录对照(重建后);
3. **消费层已有 Metabase/SQLBot**:DRG 盈亏看板可挂进现有 BI,降低培训成本。

## 三、入院诊断样表结论:结构有、业务未用

392 行(284 个住院号,一人多记录),33 字段:

- 结构上含**中医/西医"初步诊断+其他诊断"及编码共 8 个字段**——多诊断槽位存在;
- **但 392 行中 8 个诊断字段 100% 全空**:临床只填了主诉/现病史等文本(主诉/现病史仅 97 行有值),诊断编码全部留待出院后在病案首页环节;
- 含"节气"字段(中医特色),首页序列/住院号可关联病案首页。

**含义:入院环节不做结构化编码,编码集中于出院/病案环节 → 编码质控(码值合法性、主诊断选择、QY 预警)必须卡在出院与上传两个关口,入院数据不构成分组输入。**

## 四、已知问题与风险(脚本中暴露)

1. **曾发生 VARCHAR 截断故障(Msg 8152)**,涉及全部 5 张实体表,已通过"加宽列+全量重同步"修复(一键修复_所有表字段截断.sql)——说明同步链路曾脆弱,DRG 新增表务必在字段长度上留余量(诊断名称、医嘱内容等);
2. 费用快照按 (住院号+收费时间+费用类别+项目名称) 去重 + SUM 聚合,可正确处理同日多次开单与冲账(负金额净额化),但**重跑窗口边界**需在 DRG 侧复核;
3. 出院记录视图按住院号取最新一条,已处理"出院后修正/补录"重复——出院诊断文本以出院记录为准,**结构化出院诊断编码的存储位置待确认**(见下)。

## 五、新增待确认清单(数据库侧,可直接下库核实)

1. `SELECT DISTINCT 列(kind_input) FROM 源表(diagnosis)`——确认诊断类型全部取值(1/2 之外是否有出院口径),以及出院诊断最终以哪一行(列(order)/kind 组合)为准;

3. HIS 中是否有收费项目字典表(院内编码↔名称↔单价)与医保目录对照表;`列(cost_no_medicare)` 的生成逻辑;
4. 结算清单上传走什么通道(第三方接口程序?HIS 模块?)——它读取的"其他诊断"来源,即上传侧实际数据流;
5. `源表(settle)` 的粒度(一结算一行?)与和返回 Excel 结算 ID 的对应关系(列(bill_no) ↔ 结算id)。
